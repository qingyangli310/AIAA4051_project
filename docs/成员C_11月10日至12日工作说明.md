## 我完成的主要工作

### 1. 统一错误步骤编号

原协议使用 1-based 动作编号：第一个动作是 `step=1`。

我将接口统一为 0-based：

```text
第一个动作：step=0
第二个动作：step=1
第三个动作：step=2
```

采用 0-based 的原因：

- 与 Python 的 `enumerate(plan)` 和列表下标一致；
- 与现有 Python 评估代码保持一致；
- 减少 A、B、C 模块之间的编号转换；
- 降低 off-by-one error 的风险。

例如：

```text
候选路径：right, right, down
```

第二个 `right` 撞到障碍物时，统一输出：

```text
invalid | step=1 | reason=obstacle_collision
```

### 2. 统一 `goal_not_reached` 的编号

当动作全部执行完成，但最终位置不是终点时，统一使用：

```text
first_error_step = len(plan)
reason = goal_not_reached
```

这个值表示“路径结束位置”，不代表执行了额外动作。

例如：

```python
plan = ["down"]
len(plan) == 1
```

如果执行 `down` 后没有到达终点，则：

```text
first_error_step = 1
reason = goal_not_reached
```

空路径没有执行任何动作，因此未到达终点时使用 `step=0`。

### 3. 明确数据集构成

我把数据集用途整理为：

| 数据集 | 内容和用途 |
|---|---|
| Train | Generation、Verification、Repair 三种任务的训练样本 |
| Dev | 三种任务的开发样本，用于模型选择和参数调整 |
| Held-out Test | 与 Train/Dev 互斥的保护测试环境池 |
| ID 单错误条件 | Held-out Test 上的有效、可行但非最优及单错误样本 |
| OOD 双错误条件 | 同一批 Held-out Test 基础样本上的双错误样本 |

Train、Dev、Held-out Test 必须严格按 `environment_id` 划分且两两无交集。ID 与 OOD 是同一 Held-out Test 上通过 `base_sample_id` 配对的评价条件，不是两套互斥地图。

### 4. 实现端到端管线

我实现了 `run_pipeline`，负责保存和传递每一个中间结果：

```python
generation = generator.generate(grid)
candidate_plan = generation["plan"]

verification = verifier.verify(
    grid=grid,
    plan=candidate_plan,
)

if verification["valid"]:
    repaired_plan = candidate_plan
else:
    repair = repairer.repair(...)
    repaired_plan = repair["repaired_plan"]

final_result = executor.execute(
    grid=grid,
    plan=repaired_plan,
)
```

完整返回值包含：

```text
environment_id
generation
candidate_plan
verification
repair
repaired_plan
final_result
```

这样后续做实验时，可以检查模型在哪个阶段出错，而不只是看到最终成功或失败。

### 5. 设计并验证 Repair 接口

Repair 输入包含：

```text
environment_id
grid
candidate_plan
verifier_feedback
```

验证反馈固定使用：

```text
valid
first_error_step
reason
```

Repair 输出包含：

```text
raw_output
repaired_plan
parse_success
```

我增加了接口检查，用来发现：

- 网格缺少必要字段；
- `first_error_step` 不是非负整数；
- 使用了未定义的错误类型；
- `goal_not_reached` 没有使用 `len(plan)`；
- Repair 输出缺少字段；
- `repaired_plan` 不是列表；
- 已声明解析成功，但路径中仍含非法动作。

### 6. 建立可运行的 Mock 组件

由于成员 A、B 的真实模块还没有全部接入，我实现了：

- `MockGenerator`：生成一条确定的错误路径；
- `MockVerifier`：返回第一次错误的位置和类型；
- `MockRepairer`：生成一条完整修复路径；
- `MockExecutor`：重新执行修复路径并判断是否成功。

Mock 组件的作用不是模拟正式模型效果，而是提前验证所有模块是否能够按统一接口连接。
